# Local Steam compatibility on Xbox

The coverage target is 80 playable games from a 100-game Steam library. The Xbox app already uses the same install and Play workflow for every user. Extend that workflow to select a packaged runtime using the installed game build and its dependencies. The coverage report uses the account's game-only library and counts each AppID once after gameplay, controller input, audio, save and reload, and return to the library are verified on a specified Xbox build.

Valve's Proton targets Linux with Wine and graphics backends that use Vulkan. Retail Xbox Developer Mode provides a Windows x64 UWP environment with Direct3D 11 and 12, a different process and presentation model, and a documented 1 GiB app or 5 GiB game foreground budget. Reuse the components already exercised on Xbox, including Mesa's D3D12 backend and the shared SDL presenter, and establish the equivalent Windows ABI and performance requirements with Xbox controls. [Valve Proton](https://github.com/ValveSoftware/Proton) · [Xbox UWP system resources](https://learn.microsoft.com/en-us/previous-versions/windows/uwp/xbox-apps/system-resource-allocation) · [Mesa D3D12 driver](https://docs.mesa3d.org/drivers/d3d12.html)

## Runtime and launch path

1. Keep Steam responsible for entitlement, depot selection, downloads, launch options, redistributables and cloud sync. Big Picture delegates Install and Play to the app's existing authenticated Steam session.
2. Identify the installed executable and its Windows architecture, game build ID, normal and delay-loaded imports, and separately identified dynamic engine files. Group titles by shared requirements such as D3D11 and DXGI, desktop OpenGL, SDL, managed runtime, desktop windowing, media and audio.
3. Validate each shared runtime in a signed test package on Xbox. Publish it with the app. Resolve support by runtime version and game build while using the same native presentation, controller, audio, save and lifecycle services across backends. Use a title profile only for input such as the publisher's launch option or a dynamically loaded engine filename. Give incompatible builds a launch diagnostic and keep game depots and user saves intact.
4. Reuse each successful runtime across the corresponding group. A new game or Steam update can change its dependency graph, so record evidence against the exact build and repeat the play checks before counting it. Run a short set of representative controls on every runtime release and verify each title it adds to the 80-game target.

Start with Windows x64 titles whose requirements fit existing Xbox services. Desktop GL requires a test that resolves an ordinary Windows import and draws a frame. A D3D11 or D3D12 control should render into the app's presenter and survive controller input, focus changes and return to the library. A guest runtime for x86, kernel-dependent middleware, and other unsupported desktop services has a separate feasibility boundary. Stage the recipe, launch profile, and adapter declaration with `python3 -m build_tools.prepare_big_picture_library --win32-trial-profile APPID=DIRECTORY`. The checksum-pinned x64 Steam Core artifact supplies the native component with its matching WinRT metadata and adapters.

For each AppID, place the recipe in `steam-win32-shadow-APPID.xwp`. The signed `steam-win32-shadow-APPID.txt` contains the Steam build and launcher filename on the first two lines. The next four lines can supply a renderer, the `godot` diagnostic launcher, a different image to patch, and a source subdirectory within the installed game. Put `loader-trace` on the seventh line to enable tracing for a recipe that redirects loader imports. An optional `steam-win32-files-APPID.txt` supplies the companion paths relative to that source directory. To adapt a companion image, append a tab and its recipe key to the path. The launcher applies `steam-win32-shadow-APPID-KEY.xwp` after verifying that image's hash. Use a build profile only when the audited binaries match the files installed by Steam.

An eighth line of `accessibility=disabled` selects Godot's desktop accessibility diagnostic option. It requires an empty seventh line and a signed `opengl3` and `godot` profile paired with `--surfaceless-profile` for the same build. This lets the Win32 compatibility window render while the Windows accessibility adapter is unavailable. [Godot command-line options](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

The native launcher streams the original image through SHA-256 while writing a temporary copy. It prepares that copy and its companions after the Steam entitlement check, checks the build and entitlement again before creating the child, and removes the temporary directory after the trial. Each run gets its own directory. The signing layout contains the recipe, runtime code, and companion paths. The data comes from the player's existing Steam install.
